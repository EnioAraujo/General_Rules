Plano — Remoção do Fluxo de Aprovação de Fechamento
Contexto
O sistema atualmente implementa um ciclo de aprovação de 4 estados (rascunho → enviado → revisao → aprovado) para os fechamentos financeiros por fornecedor. O usuário solicitou a remoção total deste fluxo, sem substituto: fechamentos ficam sempre editáveis e a UI não exibe pills/botões de status.

Estado atual do código: a remoção foi iniciada em 2026-04-25 mas ficou incompleta. Existem migrations que removem a coluna status do banco e o tipo Fechamento em fechamento-utils.ts já não tem o campo. Mas:

FechamentoTab.tsx ainda importa/usa STATUS_COLORS, NEXT_STATUS, FechamentoStatus, STATUS_LABEL_KEY.
fechamento-utils.ts ainda exporta STATUS_COLORS e NEXT_STATUS (que referenciam um FechamentoStatus que já não está importado naquele arquivo — gera erros TS2304: Cannot find name 'FechamentoStatus').
api/fechamento.ts ainda mantém o tipo FechamentoStatus, campo status nas interfaces FechamentoInput/FechamentoOutput, e passa p_status para a RPC criar_fechamento (que já não aceita esse parâmetro segundo a migration 20260425_update_criar_fechamento_rpc.sql).
i18n-translations.ts mantém 7 chaves de status × 2 idiomas (pt-BR + en-US).
Testes em fechamento-utils.test.ts validam STATUS_COLORS e NEXT_STATUS.
A intenção desta limpeza é finalizar a remoção iniciada anteriormente, eliminando inconsistências entre código TypeScript, banco de dados e testes.

Riscos / Dependências Críticas
Migration destrutiva. DROP COLUMN status é irreversível sem backup. Snapshot do banco obrigatório antes da Etapa 6. Risco: se algum cliente externo (BI, planilha, integração não auditada) lê essa coluna, vai quebrar.

Política idx_fechamentos_status. A migration fechamento_api_rpc.sql cria um índice idx_fechamentos_status em fechamentos(status). Após o DROP, o índice é removido pelo PostgreSQL automaticamente, mas vale validar que a migration 20260425_remove_status_from_fechamentos.sql não tenta dropar índice manualmente após dropar a coluna (ler antes de rodar).

Perda funcional aceita. Sem status, fechamentos ficam sempre editáveis para sempre. Não há mais marcador visual indicando "este fechamento já foi enviado/aprovado". O usuário aceitou explicitamente esta perda.

Dashboard "valor pago no mês". A semântica antiga somava só status='aprovado'. A API fechamento-dashboard.ts já foi adaptada para não filtrar por status — então o cálculo atual já considera todos os fechamentos. Validar nos testes que isso continua funcionando.

Ordem entre código e DB. Se a migration rodar antes do deploy do código limpo, o frontend antigo (com status no payload) vai falhar na chamada à RPC. Se o código for deployado antes da migration, queries que ainda tentam ler status vão falhar. Estratégia segura: deploy do código primeiro (que já não envia/lê status), depois rodar a migration.

Dívida técnica pré-existente fora do escopo. Os 3 arquivos principais já passam de 200 linhas. A regra do projeto sugere divisão. Esta entrega não inclui divisão (escopo cirúrgico = só remover status). Sinalizar para próxima entrega:
